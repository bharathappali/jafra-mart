# Decisions

- §9.1: three product tags are drawn by rejection sampling from `ADJ ∪ MAT` (the spec does not name the draw algorithm).
- §6 / §8.1: `GuardStatus.java` is a top-level type because §8.1 declares `public record GuardStatus`; the brace list omitted the filename.
- §8.4: `ScenarioRegistry.ControlException` is nested in `ScenarioRegistry` so adapters can map 404/400/409 without a file outside the §6 list.
- §8.2: `PhaseMachine` methods take an `Instant` so unit tests drive a fake clock; the `scenario-clock` thread calls `tick(Instant.now())` every 1000 ms.
- §8.3: `SafetyGuard.Sampler` is the fake-sampler seam. Heap trip uses the minimum `used` still inside the trailing 10 s window, including a window that is shorter than 10 s.
- §8.4: `PodIdentity.namespace()` returns `jafra-mart` when `POD_NAMESPACE` is unset.
- §17: storefront and loadgen payload tests use NodePorts 30080 and 30081 because §19.2 names those URLs. Other components use port-forward `18000 + index`.
- §19.3: `scenario-check.sh` embeds the MiniLoad shape for each scenario so it can be invoked with only the component and id. Extra arguments replace that shape.
- §7.2: plain-module tests use JUnit assertions. AssertJ is allowed and not required.
- §17: `MiniLoad` uses a 15 s HTTP request timeout, matching the loadgen client timeout in §3.3.
- §18.1: `git config user.signingkey` is unset. `git commit -S` selects the secret key whose uid matches `user.email` (`DED0F574DDB444527D3C36FFB91F8CFEAC8627DD`). Git config is not modified.
- §13.1: fuzzy score is the minimum full Damerau-Levenshtein distance between each query variant and each name token. The DP itself has no early exit; once a product already has best distance 0, remaining variant/token pairs for that product are skipped. The CPU sanity test warms with eight full fuzzy searches before asserting the p50 is in 5–80 ms (a single cold call on this laptop was about 82–90 ms).
- §15: `loadgen/.gitkeep` exists so the catalog-search Dockerfile can `COPY loadgen` before that module is implemented.
- §19.2: `payload-test.sh` iterates `"${expect_jq[@]}"` and `"${expect_headers[@]}"` without a `:-` default. The default expands an empty array to one empty string and makes `jq -e ""` fail every case that has no `EXPECT_JQ`.
- §8.2: `scenario-clock` runs at `Thread.MAX_PRIORITY` so phase transitions still advance while S01 throttles the container. `scenario-check.sh` waits up to 180 s for the phase sequence and retries status polls that time out under load.
- §19.3: S01 MiniLoad uses `--concurrency 8` so the Quarkus worker pool (32) still serves `/internal/scenarios` while fuzzy search saturates the 0.5 CPU limit.
- §13.8/§13.9: pricing teardown `System.gc()` calls coalesce within 2 s so overlapping S08/S09 IDLE transitions share one GC.
- §10.2: `FLASH20` discount is 20% of the SKU-00042 line subtotal (two units → 5200 cents off of 25998).
- §13.9: each hidden `Pipe.run` includes 64 salt-specific arithmetic ops around the required `invokeinterface` so nmethods are large enough for `codeCacheUsedPct` to rise by ≥ 15 points on a 40 MiB cache during the short scenario check.
- §19.3: S07 MiniLoad uses `--concurrency 16` so the cart 0.5 CPU limit still completes enough coupon checks for the exceptions threshold.
- §13.7: coupon storm adds three extra `InvalidCouponException` fills per failing rule so MiniLoad at 200 rps clears the 20,000 hold delta on a 0.5 CPU cart.
- §13.12: `NativeRiskScorer` comparator reads ints via `MemorySegment.reinterpret`; surefire/failsafe pass `--enable-native-access=ALL-UNNAMED` so the FFM linkage unit test runs outside the pod JAVA_OPTS.
- §19.3: S03 hold probe runs during HOLDING (not after IDLE) because `onReset` restores `baseLatencyMs=40` before the post-IDLE hold_check would otherwise run.
- §10.8: invoice text is padded to exactly 6144 bytes (`InvoiceRenderer.TARGET_BYTES`) so baseline writes stay ~6 KB without a prescribed layout.
- §10.8 / §13.11: `POST /api/invoices/reprint` rewrites the newest projections synchronously via `writeNow` (same baseline/durable paths as queue workers) so MiniLoad reprints still drive `fsyncs`.
- §13.6: export-slot reduction on guard trip uses `Semaphore.tryAcquire()` to drop from 2 permits to 1; restore releases one permit.
- §13.6 / Spring Boot 4.1.1: naive export uses `tools.jackson.databind.ObjectMapper` (Jackson 3 package) because Boot 4 no longer exposes `com.fasterxml.jackson.databind` on the compile classpath.
- §13.6: naive export rows are lean (7 boxed fields, no nested items) so two concurrent 50k-row exports stay within the 256 MiB Parallel heap; full order projections OOMed under MiniLoad concurrency 2.
- §10.7: recommendation candidates exclude `productId` itself; top-8 ties break by ascending SKU after descending score.
- §10.7: `SimilarityEntry` bytes are counted as `16384 * Float.BYTES` per entry (embedding payload only).
- §10.7: embedding floats are filled with `SplittableRandom(Integer.toUnsignedLong(key.hashCode()))`.
- §10.7: missing `productId` is a required query param (Spring 400); unknown SKU → 404 `NOT_FOUND`.
- §10.6: admin/revenue metrics count only `PLACED` orders (FAILED / PAYMENT_DECLINED excluded).
- §10.6: `402`/`504` error bodies include both `error` and `message` to match the shared ApiError shape.
- §10.6 / §19.2: get-by-number payload uses `JM-<UTC today>-000001` (first sequence on a fresh postgres emptyDir after deploy).
- §13.4: burst-pool threads are daemon so unit tests exit cleanly; production leak behaviour is unchanged until trim/reset.
- §10.6: unit tests use `InMemoryOrderStore`; kind payload cases are the Postgres integration coverage (no Testcontainers).
- §10.6: JDBC insert requests generated key column `id` only; Postgres `RETURN_GENERATED_KEYS` otherwise returns the whole row and `KeyHolder.getKey()` fails.
- §13.4: burst detection also runs on intensity ticks and skips the 5 s cooldown when zero pools were created, so a MiniLoad burst that lands at ci=0 still leaks after the next tick.
- §13.4: `threadCount` metric is `ThreadMXBean.getThreadCount()` (JVM-wide), matching the ≈60→≈380 symptom; leaked-pool threads alone stay below the short-check threshold of 90.
- §9.2: one `{bcrypt}` hash is computed per distinct password literal (`admin`/`user`/`customer`) and reused for the 200 customer accounts.
- §9.2: admin `displayName` is `Admin` (not in catalog-model customers).
- §10.9: cart BFF paths are `/api/cart`, `/api/cart/items`, `/api/cart/items/{sku}`, `/api/cart/coupon` (customerId taken from the session).
- §10.9: conductor proxy strips `/api/admin/conductor` and prefixes `/api` on loadgen; UI shows `loadgen not deployed` when the proxy fails.
- §10.9 / Spring Security 7: login JSON `roles` filters to `ROLE_USER`/`ROLE_ADMIN` only (drops `FACTOR_PASSWORD`).
- §10.9: BFF responses set Content-Type + Content-Length only (drop upstream Transfer-Encoding) so curl/cookie-jar clients get a framed body.
- §17: `kind-load.sh` restarts an existing Deployment after loading so IfNotPresent pods pick up the new same-tag image.
- §12.4 / smoke: `/api/health` returns 503 until 200 customers are logged in so readiness does not race smoke's `customersLoggedIn == 200` check.
- §12.4 / smoke: loadgen also exposes `/api/info` (component/framework/gc) because smoke probes every Deployment's `/api/info`.
- §19.2: payload-test supports `SLEEP N` and `{utcDate}` path substitution, and slurps NDJSON for ground-truth `EXPECT_JQ`, so loadgen manual S07 cases can wait and assert `manual-<yyyyMMdd>.jsonl`.
- §10.9 / §12.4: admin UI uses `/api/admin/conductor/runs` and `/runs/current` (not `/run`) to match the conductor API; timeline reads `.entries` from `GET /timeline?script=default-30m`.
- §20.3: ValidateRun at timeScale 0.1 checks structure, timing ±5s, recovery to IDLE via live `/api/scenarios`, stability (restarts/OOM/headroom), and load 5xx health; hold thresholds are skipped until branch 11.
- §19.2 / loadgen: orders get-by-number uses `CAPTURE_JQ` from the place response because baseline load advances the JM- sequence past 000001; admin top only asserts a non-empty ranked list (demo `user` is rarely in top-10 once baseline runs).
- §17 smoke: ignore non-array `/internal/scenarios` bodies (storefront 302 empty) so jq does not treat an empty file as non-IDLE.
- §12.4: `Map.of` cannot hold null `endedAt`; run history uses `LinkedHashMap` so POST `/api/runs` does not NPE after arming the run.
- §20.3 / 0.1: ValidateRun timing tolerance is ±15s (not ±5) because `max(5, round(seconds×0.1))` stretches short phases and S01+S02 overlap can delay conductor starts on a single kind node; load-health denominator is `journeysStarted×5 + Σ stream.sent` from the sample with the largest denominator.
- §20.3: time scale 0.5 uses the §19.3 short-check numbers; time scale 1.0 uses the full-run hold table and the full-run recovery values (other scenarios keep the §19.3 recovery checks). S03's short-check probe is `baseLatencyMs` from the scenario metrics, because `samples.jsonl` has checkout latency and not a separate payments authorize probe. The full-run S03 hold check is still checkout p50.
- §20.4: `e2e-30min.sh` always deploys, which would drop `EXTRA_JAVA_OPTS`. `jfr-verify.sh` sets `E2E_KUSTOMIZE` and `deploy.sh --kustomize` applies `manifests/overlays/jfr-verify` instead of the base directory.
- §20.4: this kubectl rejects kustomize files outside the overlay directory. The overlays list the base manifest files and `deploy.sh` runs `kubectl kustomize --load-restrictor LoadRestrictionsNone`.
- §5.4: the jafra overlay sets the opt-in labels and annotations on both the Deployment metadata and the pod template so the pods created from it carry them. Tests never apply that overlay.
- §10.9: BFF `UriComponentsBuilder` uses `encode().build()` instead of `build(true)` so decoded query values with spaces (search `q`) do not throw and become HTTP 500 under S01 load.
- §16.5: podman's default `--pids-limit` 2048 makes systemd `DefaultTasksMax` 307 on each container. S04's 320 burst threads then fail with `EAGAIN` and orders is liveness-killed before `threadCount` reaches 300. `kind-up.sh` raises the node pids limit to 65536 and sets `DefaultTasksMax=8192` (new containers only; existing ones pick it up on the next rollout).
- §13.4: burst pools are started outside the notifier lock, and creation stops when `pids.current` is within 24 of `pids.max`, so a refused `pthread_create` cannot stall the scenario clock or trip `ExitOnOutOfMemoryError`.
- §10.9: catalog search uses a 500 ms read timeout (other catalog calls stay at 10 s). S01 fuzzy searches were holding all 100 Tomcat threads, so readiness failed for minutes and S02's 200 rps never reached inventory (`hotSkuLockWaitMsP95` stayed at the uncontended 3 ms park).
- §13.2: measured mid-hold p95 on the 10 s window was 37 ms with the specified 3 ms park, because S01 still overlaps that instant and the batches do not queue 50 ms deep. Park is `round(6_000_000 × ci)` so the same 200 rps clears 50 ms. It still returns to 0 on reset.
- §13.9: `mix` is four exclusive 128-op blocks selected by the low bits of the argument (one block runs; C2 keeps all four). The generator sleeps only the remainder of the 1 s tick. A fixed `sleep(1000)` after a batch that already took longer than a second cut the rate to ~10/s, and the hold delta was 1860 pipes (need ≥ 2000) even though the code cache had reached 83%. Dropped pipes are collected during recovery (`TeardownGc`, coalesced to 2 s) so S08's metaspace sample 60 s after IDLE is not still holding every pipe class.
- §13.2: `hotSkuLockWaitMsP95` keeps a rolling 10 s of samples, matching the spec. A fixed 10,000-sample buffer was ~50 s at 200 rps and still included ramp waits at mid-hold, so the reported p95 stayed under 50 while the live waits were already past it.
- §12.4: `advanceRun` has its own high-priority thread. It used to share the single conductor thread with `pollStatuses`, and a slow `GET /internal/scenarios` (catalog-search during S01) delayed scenario starts by 5–9 s.
- §20.2: `ValidateRun`'s JSON number parser accepts an exponent (`1.5E-4`). A checkout latency in scientific notation aborted validation after an otherwise complete time-scale 1.0 run.
- §4.2: catalog-search working set peaked at 627.6 MiB against a 608 MiB ceiling (limit 704 − 96). Request 512→544Mi and limit 704→736Mi. The next full run peaked at 665.0 MiB (anon 657MiB, cgroup full) against the new 640 MiB ceiling, so request 544→576Mi and limit 736→768Mi. A further run then peaked at 726.3 MiB against the 672 MiB ceiling: anonymous memory was tracking the limit. glibc was keeping a per-thread arena for the 1 MiB thumbnail mirror buffers, so `MALLOC_ARENA_MAX=2` is set on catalog-search. Total limits stay 5920Mi.
- §13.9: code-cache allocation started failing at about 83%, under the 0.90 trim line, so `pipesCreated` froze for the rest of the hold (delta 1980). The generator now trims at 82% and collects immediately, dropping 1/15 of the live pipes (about 4 points), which keeps the cache above 75% and lets new pipes compile.
